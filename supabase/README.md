# Learner profiles and story progress

The `able-flow-story-weaver` project (`ablkhmxbqfwpdrzoraxk`) had no public tables
when inspected through Supabase MCP on 2026-11-12. The migration in `migrations/`
has been applied to that project. Do not reapply it to the existing tables.

## Tables

| Table / field | Type and meaning |
| --- | --- |
| `learner_profiles.id` | UUID PK, defaults to `auth.uid()`, FK to `auth.users.id` |
| `display_name` | Required text, 1–100 characters after trimming |
| `processing_speed` | Integer scan interval in milliseconds; default 2000, range 100–60000 |
| `contrast_need` | Boolean; default false |
| `communication_modality` | Text: `text`, `aac`, `ssl`, or `combined`; default `text` |
| `created_at` | `timestamptz`; defaults to server time |
| `story_progress.id` | UUID PK, generated by the database |
| `profile_id` | UUID FK to learner profile; defaults to `auth.uid()` |
| `story_id` | Required nonblank text, up to 200 characters |
| `current_node_id` | Required nonblank text, up to 200 characters |
| `choices_made` | JSONB array; defaults to `[]` |
| `story_version` | Positive integer content version; default 1 |
| `revision` | Server revision; starts at 1 and increments atomically |
| `last_mutation_id` | UUID for idempotent retry acknowledgement |
| `updated_at` | `timestamptz`; overwritten by a server trigger on insert/update |

One progress row is allowed per `(profile_id, story_id, story_version)`. Progress writes use the revision-checked RPC, not direct upserts.
Deleting a profile cascades to its progress; deleting its Auth user cascades to
the profile. Story IDs and node IDs refer to locally embedded content, so there
is no remote story table or runtime story download.

Example choice history:

```json
[{"node_id":"garden","choice_id":"water","target_node_id":"pond"}]
```

## Ownership and anonymous authentication

Both tables have RLS enabled and four explicit owner-only policies (SELECT, INSERT,
UPDATE, DELETE). Profile ownership requires `id = auth.uid()`; progress ownership
requires `profile_id = auth.uid()`. Both UPDATE policies have USING and WITH CHECK
conditions so a user cannot transfer rows to another profile. Only authenticated
users can modify their own profiles. Progress INSERT/UPDATE grants are revoked;
only the owner-checking `save_story_progress` RPC can write progress. The
unauthenticated `anon` role receives neither table nor RPC access.

Supabase anonymous sign-ins create real Auth users with the `authenticated` role,
so these policies work without an email or password. A publishable/anon API key
alone is not an anonymous Auth session and cannot access these tables. See the
[Supabase anonymous sign-in guide](https://supabase.com/docs/guides/auth/auth-anonymous).

Anonymous sign-ins were enabled on 2026-11-12 in this project's dashboard under
Authentication → Sign In / Providers after the user completed sign-in. The setting
was saved, and the dashboard confirmed “Successfully updated settings.” The MCP
does not expose an Auth configuration tool, so this change used native browser
control. New-user signups remain enabled, manual linking remains disabled, and
email confirmation remains enabled for email sign-ins.

An optional client integration should reuse
the existing session and call `signInAnonymously()` only if no session exists.
Do not create a fresh anonymous user on each page load.

One anonymous session owns one profile. On shared classroom devices, learners
using the same browser session share that identity; separate learner isolation
requires distinct managed sessions. Clearing browser storage or signing out loses
access to an unlinked anonymous identity. The profile UUID is not a login secret
and must never be treated as authorization by itself.

## Verification

`tests/ownership.sql` passed against the deployed database through MCP. It creates
two temporary anonymous Auth identities, switches to the actual `authenticated`
Postgres role and sets each JWT subject. It verifies:

- Atomic revision creation/update, stale-revision conflicts and idempotent retry.
- Independent rows for content versions 1 and 2.
- Owner-only RPC writes and reads; another learner cannot see or delete them.
- Direct progress INSERT/UPDATE cannot bypass revision checks.
- Invalid JSON choice history is rejected; own-profile deletion cascades safely.
- Unauthenticated table reads and RPC execution are denied.

The entire test transaction rolls back. Post-test inspection confirmed both tables
contain zero rows and both have RLS enabled. The security advisor reported no
findings before anonymous sign-ins were enabled. After enabling them, the final
advisor check reports one expected `auth_allow_anonymous_sign_ins` warning for each
table: their policies deliberately include anonymous Auth users via the
`authenticated` role. The reviewed owner predicates still restrict every row to
`auth.uid()`; no public or cross-profile access is permitted. See the
[anonymous-access advisory](https://supabase.com/docs/guides/database/database-advisors?queryGroups=lint&lint=0012_auth_allow_anonymous_sign_ins).
This tests database authorization and verifies the saved dashboard setting; it
does not constitute an actual anonymous Auth endpoint sign-in test.

The optional client adapter is inlined in `index.html`, serializes background saves,
retains the latest pending state, persists ambiguous attempts for reconnect/reload,
and uses explicit revision conflicts instead of comparing device/server clocks.
Both the initial migration and the version/revision migration have been applied.
See [the current sync contract](../docs/sync.md). The adapter remains unconfigured
by default and adds no SDK download, embedded key or core runtime dependency.
